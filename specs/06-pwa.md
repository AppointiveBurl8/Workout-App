# PWA: install, offline shell, storage durability

Until this was added the app was a normal web page that happened to be
mobile-styled: no manifest, no service worker, no icons. Two things that cost:

- **The app shell needed the network.** IndexedDB worked offline, but getting to
  the code that reads it did not.
- **Browsers evict storage from sites they consider disposable.** A workout
  history that exists only in one browser's IndexedDB is exactly the kind of
  data that goes away quietly.

Installed to the home screen, plus `navigator.storage.persist()`, is the answer
to the second. The service worker is the answer to the first.

Everything here is hand-written rather than generated by `vite-plugin-pwa`. The
plugin would do the same job, but this project is on Vite 8 and the service
worker is sixty lines; a plugin in the build path is a compatibility risk for no
saving.

## Base path

`vite.config.js` sets `base: '/Workout-App/'`, so **every URL here has to resolve
under it**. Three different mechanisms do that:

| Where | How |
|---|---|
| `index.html` | `%BASE_URL%`, substituted by Vite at build time |
| `manifest.webmanifest` | relative URLs (`./`, `icons/...`), resolved against the manifest's own URL |
| `sw.js` | `self.registration.scope`, which is the directory the worker was registered from |
| `src/main.jsx` | `import.meta.env.BASE_URL` |

After a build, `dist/index.html` should show `/Workout-App/manifest.webmanifest`
and friends. If a raw `%BASE_URL%` survives, or an absolute `/something` appears,
it will 404 in production and work fine locally - check the built file, not the
source.

## Manifest

`public/manifest.webmanifest`. The values that aren't obvious:

- `start_url` and `scope` are `"./"` - relative, so they resolve to
  `/Workout-App/` without the base being hard-coded in two places.
- `theme_color` is `#4f39f6`. That is Tailwind 4's `indigo-600`, the colour of
  the primary button and the active bottom-nav card. Note it is **not**
  `#4f46e5` - Tailwind 4 moved its palette to OKLCH and `indigo-600` shifted.
  If the UI's indigo ever changes, this and the `theme-color` meta in
  `index.html` both need changing with it.
- `background_color` is `#ffffff`, which is what the app's page background
  actually is: nothing sets a `body` background, and `index.css` only declares
  `color-scheme: light dark`. *Consequence:* in dark mode the splash screen is
  white while the app itself comes up dark. A manifest has one background
  colour and no media query, so fixing that means giving the app an explicit
  background of its own first.
- `display: standalone`, `orientation: portrait`.

## Icons

`public/icons/icon.svg` is the source: a kettlebell, white on full-bleed indigo,
no transparency. The glyph sits inside the maskable safe zone (a circle of 40%
of the icon's width, centred), so the same 512px file is listed twice in the
manifest - once plain, once `purpose: "maskable"` - and a circular or squircle
mask crops only background.

`scripts/make-icons.mjs` renders it to `icon-192.png`, `icon-512.png` and
`apple-touch-icon.png` (180px, what iOS reads) with `sharp`:

```
node scripts/make-icons.mjs
```

**The generated PNGs are committed.** Run the script by hand after editing the
SVG; the build must never depend on it, or on `sharp` being installable on the
machine doing the building.

## Service worker

`public/sw.js`, registered from `src/main.jsx` on `load`, and **only in a
production build** - the dev server has no `sw.js` to serve and a worker caching
a dev bundle would fight HMR.

Three strategies, by what the request is:

| Request | Strategy | Why |
|---|---|---|
| `mode === 'navigate'` (page loads) | **Network first**, cached `index.html` on failure | An online launch must always get the newest build; the cached shell is only there so an offline launch works at all |
| same-origin under `/assets/` | **Cache first** | Vite hashes these, so a changed file gets a new name - the cached copy can never be stale |
| anything else same-origin (icons, manifest, favicon) | **Stale while revalidate** | Show instantly, refresh behind |
| **cross-origin** | **Not handled at all** - no `respondWith` | Firebase auth and Firestore must never be answered from a cache, or served stale, or silently broken by the worker. The handler returns early on any other origin |

`install` pre-caches the shell and calls `skipWaiting()`; `activate` deletes
every cache that isn't the current one and calls `clients.claim()`, so the
worker controls the very first load rather than waiting for a second visit.

**Bump `CACHE` (`workout-tracker-v1` → `-v2`) only when the `SHELL` list
changes.** Ordinary code changes don't need it: hashed asset names make the
cache self-invalidating, and `index.html` is network-first.

*Known wart:* nothing prunes old hashed assets. `activate` drops whole caches by
name, and within the current cache a previous build's `/assets/` entries just
sit there. Bounded by how often the app deploys and how big the bundle is; worth
revisiting if the bundle ever gets code-split.

## Deep links

`/Workout-App/tracker` has to resolve to the app on a refresh. Two mechanisms,
and they cover different cases:

- **Online:** GitHub Pages serves `public/404.html`, which re-encodes the path
  into a query string and redirects to `index.html`, where an inline script in
  the `<head>` restores it before React Router mounts. This predates the service
  worker (it's why `BrowserRouter` is usable on Pages at all).
- **Offline:** the navigate handler falls back to the cached `index.html`, and
  React Router reads the real path straight off the URL. No redirect needed.

## Persistent storage

`navigator.storage.persist()` is called once at startup, unconditionally and
with the result ignored. Granting it is at the browser's discretion - engagement
heuristics on Chrome, installation on Safari - and there's nothing useful to do
when it's refused. It is a request not to evict IndexedDB, which is the only
copy of a workout history that hasn't been exported or synced.

## iOS caveats

None of this is verified on a device - there is no iPhone in the sandbox this
was built in.

- **An installed home-screen app may not share Safari's storage.** If that holds,
  adding the app to the home screen gives it an empty IndexedDB, and the history
  built up in Safari stays in Safari. **Export a backup, or sign in to cloud
  sync, before re-adding the icon** - then import or sync inside the installed
  app. Treated as a real risk rather than a certainty; it needs checking on the
  device.
- Removing and re-adding the home-screen icon is the only reliable way to pick
  up a changed icon or manifest - iOS caches both aggressively.
- `apple-mobile-web-app-status-bar-style: black` gives a black status bar band
  above a standalone launch. With `viewport-fit=cover` already set and the
  bottom nav padded with `env(safe-area-inset-bottom)`, that should leave the
  app clear of both the notch and the home indicator - unverified.
- A wake lock and wall-clock timing are separate concerns; see
  `specs/04-tracker.md`. In particular the "a rehydrate does not catch up" rule
  there is unaffected by any of this - a relaunch, installed or not, resumes
  from the mirrored session rather than fast-forwarding.

## Changelog

- **Added** - manifest, generated icons, a hand-written service worker and
  `navigator.storage.persist()`. Verified with Playwright against
  `vite preview`, 20/20: the manifest parses with the right colours and a
  maskable icon; every referenced icon is served; the worker registers at the
  app scope, activates, and controls the first load; the cache holds the shell
  and nothing cross-origin; offline, both a reload and a deep link still render
  the app and read existing IndexedDB data; and a cross-origin request works
  online and fails offline rather than being answered from a cache.
- **Fixed** - `index.html`'s favicon link was an absolute `/favicon.svg`, which
  resolved off the `/Workout-App/` base and 404'd in production. Now
  `%BASE_URL%favicon.svg`. Found while checking that every href in the built
  `index.html` resolves under the base.
